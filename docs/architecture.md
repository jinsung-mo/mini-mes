# 설계 결정: 왜 이렇게 만들었나

아키텍처와 기술을 왜 이렇게 골랐는지 정리한 문서입니다. 단계별 기록은 [01-legacy.md](01-legacy.md), 실제로 겪은 문제는 [troubleshooting.md](troubleshooting.md)에 있습니다.

## 한 문장으로

**화면과 DB는 그대로 두고 WAS만 바꾼다. 바꾸는 동안에도 공장은 돌아가야 한다.**

운영 중인 시스템을 전환할 때는 새 코드를 잘 짜는 것만큼, 지금 돌아가는 것을 깨지 않는 일이 어렵습니다.
현장 단말과 설비는 지금의 응답 형식에 맞춰 만들어져 있고, 공장은 전환이 끝나기를 기다려 주지 않습니다. 아래 결정은 모두 이 조건에서 나왔습니다.

## 가장 중요한 부분: WAS를 바꿔도 화면과 DB는 모르게 한다

```
단말 화면 ──▶ nginx ──────────┬─ /legacy/api/... → C# 레거시 ─┐
 (그대로)    (전환 스위치)     └─ /java/api/...   → Java      ─┴─▶ PostgreSQL (그대로)
```

세 가지가 함께 이 구조를 만듭니다.

| 장치 | 하는 일 |
|---|---|
| **응답 계약 고정** | HTTP 200 + `resultCode`, snake_case 키, 에러 코드, 검증 순서까지 레거시와 똑같이 맞춘다. 화면은 어느 WAS가 답했는지 구분할 수 없다 |
| **nginx 경로 전환** | 화면은 주소 앞부분(`/legacy`, `/java`)만 고른다. 요청을 어느 WAS로 보낼지는 nginx가 정한다 |
| **같은 DB** | 두 WAS가 같은 테이블을 읽고 쓴다. 전환하는 동안 데이터를 옮기거나 맞출 필요가 없다 |

### 이게 가장 중요한 이유

이 구조가 있어야 전환이 **맞았는지 확인할 수 있고**, **하나씩 옮길 수 있고**, **틀렸을 때 되돌릴 수 있습니다.**

- **확인**: 같은 요청을 두 WAS에 보내서 응답을 비교합니다. 지금까지 기준정보 13건, 작업지시·LOT 조회 44건(조회 17 + 검증 실패 27), 실적 보고 33건이 C#과 같았습니다. 동시 보고 문제도 같은 요청을 양쪽에 보내서 재현했습니다.
- **하나씩 옮기기**: 지금은 화면 상단 스위치로 WAS를 고르지만, nginx의 `location`을 API 경로별로 나누면 옮긴 API만 Java로 보낼 수 있습니다. 큰 시스템을 한 번에 바꾸지 않고 기능 단위로 넘기는 Strangler Fig 방식입니다.
- **되돌리기**: Java 쪽에 문제가 생기면 nginx 경로만 되돌립니다. 화면을 다시 배포하거나 데이터를 복구할 필요가 없습니다.
- **섞어 쓰기**: C#으로 만든 작업지시를 Java로 시작하고 다시 C#으로 실적을 보고해도 됩니다. 두 WAS가 함께 도는 실제 전환 기간을 그대로 재현할 수 있습니다.

### 치른 비용

| 비용 | 내용 |
|---|---|
| REST 관례를 따르지 않음 | 실패도 HTTP 200. 바꾸려면 단말과 합의해서 따로 진행해야 함 |
| Spring 기본 동작을 레거시에 맞춰야 함 | ASP.NET과 요청 해석이 달라서 setter DTO, Jackson 설정, 404 처리 등을 손봄 ([개발 중 만난 문제](troubleshooting.md#개발-중-만난-문제)) |
| 스키마를 바꿀 때 두 WAS를 함께 고려 | LOT 채번 테이블을 넣을 때, 레거시가 만든 번호와 겹치지 않게 `GREATEST`를 둠 ([트러블 슈팅 1](troubleshooting.md#1-동시-보고-시-lot-번호-중복)) |
| 네트워크 동작까지 같아야 함 | `localhost`의 IPv6 루프백 차이 때문에 Java만 2초 늦었음 ([트러블 슈팅 4](troubleshooting.md#4-localhost-요청만-2초씩-지연)) |

## WAS 안에서 가장 중요한 부분: 실적 보고 트랜잭션

실적 보고 한 건이 LOT, 실적, 작업지시 수량, 작업지시 상태를 함께 바꿉니다.
하나라도 어긋나면 "실적은 있는데 LOT이 없다", "완료됐는데 수량이 계획보다 많다" 같은 데이터가 생기고, 생산 집계와 품질 추적이 틀어집니다.

```
ProductionService.report   @Transactional
 0. 요청 검증: 필수값(E001), 수량(E002), 보고 시각(E001)        DB에 가기 전
 1. 작업지시 행 잠금 (FOR UPDATE), 존재(E004)·진행 중(E006)     같은 작업지시의 보고는 한 줄로
 2. 설비(E009), 불량 코드(E007, E008)
 3. 근무조·근무일자 계산
 4. LOT 채번 (채번 행 잠금)                                     같은 공장·근무일자의 채번은 한 줄로
 5. LOT 저장, 실적 저장
 6. 작업지시 수량 누적, 계획 수량에 닿으면 자동 완료
 7. 커밋 → 잠금 해제
```

- 1~6 중 어디서든 예외가 나면 전부 롤백됩니다.
- 잠금 순서는 항상 작업지시 → 채번입니다. 모든 보고가 같은 순서로 잠그므로 교착(deadlock)이 생기지 않습니다.
- 두 잠금은 처음부터 있던 것이 아닙니다. 동시 보고를 재현해서 찾은 문제를 고치면서 생겼습니다 ([트러블 슈팅 1·2](troubleshooting.md#요약)).

## 결정별 이유

### 3-tier로 나누고, 그중 WAS만 바꾼다

화면·WAS·DB를 따로 실행되는 단위(tier)로 나눴습니다. 바꾸는 범위를 WAS 하나로 좁혀야, 결과가 달라졌을 때 원인이 WAS에 있다고 확신할 수 있습니다.
화면이나 스키마까지 같이 바꾸면 무엇 때문에 달라졌는지 가를 수 없습니다.

### 전환 스위치는 nginx에 둔다

어느 WAS로 보낼지 정하는 곳은 전환 대상 바깥에 있어야 합니다. 스위치를 Java 안(예: Java로 만든 게이트웨이)에 두면, Java가 멈췄을 때 레거시로 되돌릴 방법도 같이 멈춥니다.
nginx를 앞에 두면 화면과 API가 같은 주소(`localhost:3000`)라서 CORS 설정이 필요 없고, 응답 헤더(`X-Upstream`)로 어느 WAS가 답했는지도 볼 수 있습니다.

### 같은 DB를 쓴다

WAS를 바꾸는 동안 데이터를 옮기지 않기 위해서입니다. 두 WAS가 같은 DB를 쓰니 섞어 써도 되고, 문제가 생기면 경로만 되돌리면 됩니다.
대신 스키마는 두 WAS가 모두 버틸 수 있게 바꿔야 합니다. LOT 채번 테이블은 Java만 쓰고 레거시는 모르기 때문에, Java가 레거시가 만든 번호를 건너뛰게 했습니다.

### WAS 안은 Controller / Service / Mapper로 나눈다

레거시는 컨트롤러 하나에 요청 처리, 검증, 업무 규칙, SQL이 모두 들어 있습니다([레거시 문제점 1](../legacy-csharp/README.md#일부러-넣은-레거시-문제점)).
업무 규칙을 Service에 모아 두면 요청이 어디서 오든 같은 규칙을 거칩니다. 4단계에서 설비가 TCP로 보내는 실적도 REST와 같은 `ProductionService.report`를 거치게 할 계획입니다.
트랜잭션 경계(`@Transactional`)도 Service에 있어서, 어디까지 함께 롤백되는지가 코드에 드러납니다.

### 기능별로 패키지를 나누고, 다른 기능은 Service로만 부른다

`master`(기준정보), `workorder`(작업지시), `production`(실적)으로 나눴습니다. 실적 보고가 작업지시를 읽고 바꿀 때도 작업지시 테이블을 직접 건드리지 않고 `WorkOrderService`에 맡깁니다.
나중에 MSA로 서비스를 나눌 때 이 경계를 그대로 쓸 수 있습니다. 같은 이유로 "계획 수량에 닿으면 자동 완료" 규칙은 실적 쪽이 아니라 작업지시 쪽(`WorkOrderService.applyResult`)에 있습니다.

### 옮기기와 고치기를 나눈다

레거시 동작을 버그까지 그대로 옮기고, 같은지 확인한 뒤에 고칩니다. 옮기면서 고치면 결과가 달라졌을 때 그게 전환 실수인지 의도한 수정인지 구분할 수 없습니다.

동시 보고 문제도 이 순서로 다뤘습니다.

1. C#과 Java에서 같은 버그가 재현되는 것을 확인했습니다. → 옮기기는 맞았다
2. Java만 고쳤습니다.
3. 동시성이 없는 일반 요청은 고친 뒤에도 C#과 33건 모두 같은지 확인했습니다. → 고치기가 다른 동작을 바꾸지 않았다

## 기술 선택

| 영역 | 선택 | 고른 이유 | 고르지 않은 것 |
|---|---|---|---|
| 전환 후 WAS | Java 17, Spring Boot 4.0.9 | 전환 목표 스택. 국내 기업 Java 백엔드에서 널리 쓰이고 전자정부 표준프레임워크도 Spring 기반. Java 17은 Spring Boot 4의 최소 버전 | Spring Boot 4.1: MyBatis 스타터가 아직 지원하지 않음 |
| SQL 매핑 | MyBatis | 레거시 SQL을 거의 그대로 옮길 수 있어서 "같은 SQL이 같은 순서로 실행되는가"를 확인하기 쉬움. `FOR UPDATE`, `ON CONFLICT`, `RETURNING` 같은 DB 기능을 그대로 씀(트러블 슈팅 1·2의 해결이 모두 SQL 한두 줄). 6단계에서 실행 계획을 보고 SQL을 바로 고칠 수 있음 | JPA: 영속성 컨텍스트가 SQL 실행 시점과 횟수를 바꿔서 레거시와 비교하기 어렵고, 집계·잠금 쿼리는 결국 네이티브 쿼리가 필요 |
| DB | PostgreSQL 16 | `TIMESTAMPTZ`로 시점을 저장해서 공장 시간대와 상관없이 같은 순간을 같은 값으로 기록. 행 잠금, upsert, `EXPLAIN ANALYZE`. Docker로 바로 띄움 | Oracle: 기업 시스템에서 많이 쓰지만 로컬에서 띄우기 번거로움. 여기서 쓴 기능(행 잠금, upsert는 `MERGE`)은 Oracle에도 있음 |
| 전환 스위치 | nginx | 경로 기반 리버스 프록시. 전환 대상 바깥에 있음 | Java로 만든 게이트웨이: Java가 멈추면 되돌릴 방법도 멈춤 |
| 단말 화면 | HTML/CSS/JS, 빌드 도구 없음 | 화면은 전환 대상이 아니라 "바뀌지 않는 클라이언트". 빌드 없이 nginx가 파일을 바로 내려줌 | React 등: 화면은 이 프로젝트의 주제가 아님 |
| 레거시 WAS | C# .NET 8, ASP.NET Core, Npgsql | 전환 출발점인 C#을 재현. ORM 없이 컨트롤러에 SQL 문자열을 쓰는, 레거시에서 흔한 모양 | |
| 실행 환경 | Docker Compose | DB와 nginx를 명령 하나로 같은 상태로 띄움 | |
| 재현 스크립트 | Python 표준 라이브러리 | 두 WAS를 똑같이 HTTP로만 부르므로 WAS 언어와 무관. 설치할 것이 없음 | JUnit 통합 테스트: Java WAS만 시험할 수 있음 |
