# 3단계: 동등성 검증 자동화

이 프로젝트의 두 번째 질문, **"옮긴 코드가 레거시와 똑같이 동작한다는 것을 무엇으로 보여 주나"** 에 대한 답입니다.
한 명령으로 C# 레거시와 Java에 같은 시나리오를 보내고, 응답과 DB에 남은 결과를 비교합니다.

```bash
python scripts/equivalence.py
```

## 결과

| 비교 대상 | 건수 | 결과 |
|---|---|---|
| 요청 | 160건 | 같음 156, 의도한 차이 4 |
| DB (테이블 10개, 시퀀스 2개) | 12개 | 같음 11, 의도한 차이 1 |

- 2단계에서 손으로 비교한 90건으로는 보이지 않던 **차이 12건**을 찾았습니다. 10건은 Java를 고쳐 맞췄고, 2건(HEAD·OPTIONS)은 이유를 적어 의도한 차이로 남겼습니다. ([찾은 차이와 처리](#찾은-차이와-처리))
- 검증 도구도 검증했습니다. 일부러 넣은 전환 실수 5가지 중 4가지를 잡습니다. 그중 1가지(`updated_at` 누락)는 처음에 놓쳐서 도구를 고쳤고, 잡지 못하는 1가지는 이 도구의 범위 밖인 동시성 문제입니다. ([검증 도구를 검증하기](#검증-도구를-검증하기))

## 왜 만들었나

2단계에서는 같은 요청을 C#과 Java에 보내는 스크립트를 그때그때 만들어서 비교했습니다(기준정보 13건, 작업지시·LOT 조회 44건, 실적 보고 33건). 여기에는 한계가 세 가지 있었습니다.

1. **두 WAS가 같은 DB를 씁니다.** 등록·변경 요청을 양쪽에 보내면 두 번 반영되어서, 각자 작업지시를 따로 만들어 써야 했습니다. 그래서 wo_id, 작업지시 번호, LOT 번호는 가리고 비교했고, **채번 로직은 사실상 비교하지 못했습니다.**
2. **응답만 봤습니다.** DB에 무엇이 남았는지(롤백됐는지, 시퀀스를 몇 개 썼는지)는 보지 않았습니다.
3. **일회성이었습니다.** 다음 단계에서 시간대 계산을 고치고 설비 인터페이스를 붙이면 Java가 계속 바뀝니다. 그때마다 의도하지 않은 차이가 생기지 않았는지 한 명령으로 확인할 수 있어야 합니다.

## 어떻게 비교하나

```
                 db/init 스크립트 (같은 초기 상태)
                  │                          │
          mes_equiv_legacy             mes_equiv_java
                  │                          │
          C# 레거시 :5180               Java :8181
                  ▲                          ▲
                  └── 같은 요청을 같은 순서로 ──┘
                      scripts/equivalence.py
```

1. 두 WAS를 빌드합니다. (C# Release, Java bootJar)
2. 검증용 DB 두 개를 지우고, `db/init` 스크립트로 새로 만듭니다. Docker가 처음 DB를 만들 때와 같은 스크립트, 같은 순서입니다.
3. 검증용 포트에 WAS를 하나씩 띄웁니다. 설정 파일은 그대로 쓰고 포트와 DB만 명령줄 설정으로 바꿉니다.
4. 시나리오의 요청을 하나씩 C# → Java 순서로 바로 이어서 보내고 응답을 비교합니다.
5. 두 DB를 비교하고, WAS를 내립니다.

개발용 WAS(:5080, :8081)와 개발용 DB(`mes`)는 건드리지 않습니다.

### 검증할 때는 DB를 나눈다

운영 전환에서는 두 WAS가 같은 DB를 씁니다. 그래야 섞어 쓸 수 있고 nginx 경로만 바꿔 되돌릴 수 있습니다([설계 결정](architecture.md#같은-db를-쓴다)).
검증은 반대로 DB를 나눕니다. 같은 스크립트로 만든 같은 상태의 DB에서 출발해 같은 요청을 같은 순서로 보내면, 두 WAS가 맞게 동작하는 한 시퀀스와 채번 결과도 같아야 합니다.
그래서 `wo_id`, `WO-KR01-20261103-001`, `L-KR01-261103-0001`까지 가리지 않고 그대로 비교합니다.

### 무엇을 같다고 보나

| 대상 | 비교 방법 |
|---|---|
| 응답 (`resultCode` 형식) | HTTP 상태, `resultCode`, `message`, `data` 전체. 키 순서는 보지 않고, 숫자 `1`과 문자열 `"1"`은 다르게 봄 |
| 응답 (그 밖의 HTTP 오류) | HTTP 상태만. 본문은 ASP.NET과 Spring이 각자 만드는 오류 문서이고, 단말 화면도 이때는 HTTP 상태만 보여 줌 ([`app.js`](../web/html/app.js)) |
| DB 테이블 | `public` 스키마의 모든 테이블의 모든 행. 기본키 순서로 읽음. 테이블 목록을 DB에서 읽어서 새 테이블이 생겨도 비교에서 빠지지 않음 |
| DB 시퀀스 | 마지막 값. 실패해서 롤백된 요청도 시퀀스는 씀. 검증·저장 순서가 레거시와 다르면 여기서 어긋남 |
| 서버 시각 값 | `started_at`, `completed_at`, `created_at`, `updated_at`, `reported_at`은 2초 안이면 같다고 봄 |

서버 시각이 들어가는 값은 두 WAS가 몇 ms 차이로 처리하고 응답은 초 단위라 똑같을 수 없습니다. 그래서 2초까지는 같다고 봅니다.
이 허용 범위가 실수를 가리지 않도록 확인했습니다. 시간대를 잘못 다루면 몇 시간씩 어긋나고, 다른 상태 전이에서 시각을 채우면 한쪽만 값이 있습니다. 시각을 아예 안 바꾸는 실수는 처음에 가려졌는데, 시나리오를 고쳐서 잡게 했습니다([아래](#검증-도구를-검증하기)).

### 시나리오는 레거시의 특성 테스트이기도 하다

[`scripts/equivalence_scenario.py`](../scripts/equivalence_scenario.py)의 요청마다 **C# 레거시가 돌려줘야 하는 결과**를 함께 적었습니다.

```python
s.post("순서: 계획일 + 수량 → E001", WORK_ORDERS, work_order(planDate="x", planQty=0), "E001")
s.post("planQty 문자열 \"4\"", WORK_ORDERS, {**no_item, "planQty": "4"}, "E003")
```

C#이 적은 결과와 다르게 답하면 Java와 비교하기 전에 `기대와 다름`으로 멈춥니다. 시나리오가 레거시를 잘못 이해했거나 레거시가 바뀌었다는 뜻입니다.
덕분에 시나리오 파일이 레거시가 지금 어떻게 동작하는지 적어 둔 문서(특성 테스트, characterization test) 역할도 합니다. C#은 처음부터 모든 요청에 적어 둔 결과대로 답했습니다.

| 구간 | 요청 | 내용 |
|---|---|---|
| 기준정보 조회 | 13 | 5개 API, 필수값 누락 |
| 작업지시 생성 | 21 | 공장·계획일별 채번, 계획일 형식, 검증 순서 |
| 요청 JSON 해석 | 19 | 소수, null, 숫자 칸의 문자열, 문자열 칸의 숫자, 모르는 키, 깨진 JSON, Content-Type |
| 작업지시 조회 | 13 | 목록 필터, 없는 작업지시, 숫자가 아닌 id |
| 상태 전이 | 22 | 허용·거절되는 전이, 수동 완료 |
| 실적 보고: 검증 | 29 | 오류 코드 7가지와 검증 순서 |
| 실적 보고: 반영 | 21 | 근무조 경계(06·14·22시), 자정 넘김, LOT 채번, 자동 완료, 앨라배마 시간대 버그, DB 오류(E999) 롤백 |
| 반영 결과 조회 | 10 | 위 반영 결과를 조회 API로 |
| 주소·파라미터 표기 | 6 | 끝 슬래시, 대소문자, 같은 파라미터 두 번 |
| HTTP 오류 | 6 | 없는 주소, 지원하지 않는 메서드 |

시나리오를 짤 때 지킨 것:

- **한쪽만 성공하는 요청을 만들지 않는다.** 한쪽만 성공하면 두 DB가 갈라져서 그 뒤의 비교가 줄줄이 어긋납니다. 요청 해석 방식만 보려는 요청은 해석에 성공해도 뒤쪽 검증(없는 품목, E003)에서 걸리게 만들었습니다.
- **날짜를 고정한다.** 계획일과 보고 시각을 2026-11-03으로 고정해서 언제 실행해도 같은 번호가 나옵니다.
- **롤백도 확인한다.** 누적 수량이 int 범위를 넘으면 LOT과 실적을 저장한 뒤 DB 오류(E999)가 납니다. 이후 조회와 DB 비교에서 LOT·실적·수량이 남지 않았는지, 두 WAS가 시퀀스를 같은 수만큼 썼는지 봅니다.

### 의도한 차이

레거시와 일부러 다르게 만든 동작은 `KNOWN_DIFFERENCES`에 이유와 문서를 함께 등록합니다. **여기 없는 차이는 모두 전환 실수로 봅니다.**

| 의도한 차이 | C# 레거시 | Java | 이유 |
|---|---|---|---|
| E999 응답 메시지 | 예외 메시지를 그대로 응답 | 참조 번호만 응답 | 서버 내부 정보 노출을 고침 ([트러블 슈팅 3](troubleshooting.md#3-오류-응답에-서버-경로와-sql-노출)) |
| 보고 시각 형식 | `DateTime.TryParse`가 받는 형식 모두 | ISO 형식만 | 서버 문화권에 따라 해석이 달라져서 따라 하지 않음 ([2단계](../mes-api/README.md#실적-보고-기능-경계를-넘는-요청)) |
| LOT 채번 테이블 `lot_seq` | 안 씀 (`MAX + 1`) | 공장·근무일자별 마지막 순번 | 동시 보고 시 번호 중복을 고침 ([트러블 슈팅 1](troubleshooting.md#1-동시-보고-시-lot-번호-중복)) |
| HEAD·OPTIONS 요청 | 405 | 200 | [의도한 차이로 둔 것](#의도한-차이로-둔-것) |

등록만 해 두고 넘어가지 않도록, 의도한 차이도 **어떤 모양이어야 하는지** 확인합니다.

- 요청에는 Java가 돌려줄 결과를 함께 적습니다(`known=("reported-at-format", "E001")`). 차이가 사라지거나 다른 모양이 되면 `다름`입니다.
- `lot_seq`는 C# 쪽이 비어 있는지, Java 쪽의 마지막 순번이 발행된 LOT 번호의 마지막 순번과 같은지 확인합니다.

## 찾은 차이와 처리

처음 실행에서 6건이 나왔고, 같은 원인의 다른 모양을 찾으려고 주변 요청을 더 넣어서 6건이 더 나왔습니다. 모두 ASP.NET과 Spring의 기본 동작 차이였습니다.
2단계에서 손으로 비교할 때는 단말 화면이 실제로 보내는 요청 위주라, 주소·파라미터 표기를 바꿔 보는 요청은 보내지 않았습니다.

### 판단 기준

1. **레거시가 받던 요청을 Java가 거절하면 맞춘다.** 그대로 두면 지금 쓰는 클라이언트가 깨집니다.
2. **레거시가 거절하던 요청을 Java가 처리해도 맞춘다.** 레거시에서 오류였던 요청으로 Java에서는 데이터가 만들어질 수 있습니다. 단, 데이터를 읽기만 하는 HTTP 표준 동작은 의도한 차이로 둡니다.
3. **레거시 동작이 환경에 따라 달라 따라 할 수 없으면 의도한 차이로 두고 거절한다.** (보고 시각 형식, 2단계에서 결정)

### 맞춘 것

| 요청 | C# (ASP.NET) | Java (수정 전) | 원인 | 맞춘 방법 |
|---|---|---|---|---|
| `GET /api/plants/`, `POST .../release/` | 처리 | 404 | Spring 6부터 끝에 슬래시가 붙은 주소를 다른 주소로 봄 | `UrlHandlerFilter`로 슬래시를 떼고 넘김 (리다이렉트하지 않음) |
| `GET /API/Plants` | 처리 | 404 | Spring의 주소 매칭은 대소문자를 구분 | `PathPatternParser.setCaseSensitive(false)` |
| `?plantcd=KR01`, `?PLANTCD=KR01` | 처리 | E001 | `@RequestParam`은 이름의 대소문자를 구분 | [`LegacyQueryParameterFilter`](../mes-api/src/main/java/com/minimes/common/LegacyQueryParameterFilter.java) |
| `?plantCd=KR01&plantCd=US01` | 울산 품목 | 빈 목록 | Spring은 두 값을 `"KR01,US01"`로 이어 붙임 | 같은 필터에서 첫 값만 남김 |
| `"plantCd": 1`, `"plantCd": 1.5`, `"itemCd": true` | 400 | E003 (`"1"`로 바꿔 처리) | Jackson은 숫자·true/false를 문자열 칸에 문자열로 바꿔 넣음 | Jackson 변환 설정(coercion)으로 거절 |
| 본문도 Content-Type도 없는 POST | 415 | 400 | Spring은 Content-Type보다 본문이 없다는 것을 먼저 처리 | `GlobalExceptionHandler`에서 415 |

설정은 [`LegacyRequestConfig`](../mes-api/src/main/java/com/minimes/common/LegacyRequestConfig.java)에 모았습니다. 2단계에서 맞춘 JSON 키 대소문자, 숫자 칸의 소수 거절과 같은 종류입니다([mes-api README](../mes-api/README.md#레거시aspnet와-동작을-맞춘-부분)).

[`LegacyRequestConfigTest`](../mes-api/src/test/java/com/minimes/common/LegacyRequestConfigTest.java)는 C#과 DB 없이 이 설정이 빠지지 않았는지 확인합니다. 설정을 빼고 돌리면 6개 중 4개가 실패하는 것을 확인했습니다. 나머지 2개는 레거시와 같던 동작(숫자 칸의 문자열 `"4"`, 빈 본문 400)이 이 설정 때문에 바뀌지 않았는지 지킵니다.

### 의도한 차이로 둔 것

**HEAD·OPTIONS 요청**: C#은 405, Java는 200입니다. Spring MVC는 GET 주소에 대한 HEAD(본문 없는 GET)와 OPTIONS(허용 메서드 안내)를 알아서 처리합니다.

- 데이터를 읽기만 하는 HTTP 표준 동작이라 아무것도 바꾸지 않습니다.
- 레거시에서는 늘 실패하던 요청이라 여기에 기대는 클라이언트가 없습니다.
- 막으려면 표준 동작을 끄는 코드를 따로 넣어야 하고, 상태 확인에 HEAD를 쓰는 모니터링 도구도 함께 막힙니다.

## 검증 도구를 검증하기

"모두 같음"이 의미가 있으려면 틀린 코드를 넣었을 때 실제로 `다름`이 나와야 합니다. 전환할 때 실제로 저지를 만한 실수를 Java에 하나씩 넣고 돌렸습니다.

| 넣은 실수 | 결과 | 잡힌 곳 |
|---|---|---|
| 계획 수량을 계획일보다 먼저 검증 | 잡음 | `순서: 계획일 + 수량` 요청: C# E001 / Java E002 |
| 근무조 경계를 `hour < 14`에서 `hour <= 14`로 | 잡음 | 14:00 보고 응답, 실적 이력, DB `production_result.shift_cd` |
| `started_at`을 서울 시각 대신 UTC로 보여 줌 | 잡음 | 작업 시작 응답 12건 (9시간 차이) |
| 실적 반영 때 `updated_at`을 안 바꿈 | **처음엔 못 잡음** → 잡음 | DB `work_order.updated_at` |
| 작업지시 행 잠금(`FOR UPDATE`) 제거 | 못 잡음 (범위 밖) | 요청을 하나씩 보내서는 드러나지 않음. [`report_race.py`](../scripts/report_race.py)의 `complete` 시나리오가 잡음 ([트러블 슈팅 2](troubleshooting.md#2-완료된-작업지시에-실적이-계속-반영됨)) |

`updated_at`은 처음에 놓쳤습니다. 그때는 서버 시각 값을 5초까지 같다고 봤는데, 작업 시작과 실적 반영 사이가 2초가 안 돼서(요청 48건, 약 1.7초) "시각을 안 바꾸는" 실수가 허용 범위에 가려졌습니다.
허용 범위를 2초로 줄이고, 시각이 바뀌어야 하는 단계 앞(상태 전이 전, 실적 반영 전)에서 3초씩 쉬게 했습니다. 그 뒤로는 잡힙니다. 쉬는 시간 때문에 한 번 돌리는 데 6초가 늘었습니다.

## 요청 추가하기

```python
s.post("요청 이름", "/api/work-orders", work_order(planQty=10), "C#의 결과 코드", save={"wo_x": "data.wo_id"})
s.get("저장한 값 쓰기", "/api/work-orders/$wo_x")
```

1. C#이 적은 결과대로 답하는지 확인합니다. 다르면 시나리오부터 고칩니다.
2. Java가 C#과 같은지 봅니다. 다르면 전환 실수이므로 Java를 고칩니다.
3. 레거시와 일부러 다르게 만든 동작이면 `KNOWN_DIFFERENCES`에 이유와 문서를 적고, 그 요청에 `known=(ID, Java의 결과)`를 답니다.
